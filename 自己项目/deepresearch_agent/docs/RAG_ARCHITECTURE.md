# 深度研究助手 RAG 简要架构

状态：首版已实现，文档检索及文档与网页结合的真实 HTTP 研究流程已验证通过。现有架构见 [DESIGN.md](DESIGN.md)。

## 1 目标与流程

用户上传研究资料，系统结合文档内容和网页信息，生成可追溯来源的研究报告。

**上传资料 → 解析、分块、向量入库 → 研究规划 → 每个子任务分别检索本地资料和网页 → 整理证据 → 总结 → 汇总报告**

文档导入与研究执行分开：选择 PDF 后自动导入并关联到当前研究；不添加资料时，继续使用现有联网研究流程。当前页面支持保留已关联资料继续研究，刷新或重新打开页面后需重新上传。

```text
资料准备
上传 PDF → 解析与分块 → Embedding → Qdrant 知识库
                                         ↑
研究执行                                 │
研究主题 + 可选知识库 → 规划子任务 → 按子任务查询检索
                                    ├─ 文档检索 → 相关片段与出处
                                    └─ 网页搜索 → 网页内容与 URL
                                              ↓
                                     整理证据与控制上下文
                                              ↓
                                  任务总结 → NoteTool 笔记
                                              ↓
                                     汇总报告与参考来源
```

## 2 模块职责

| 模块 | 职责 | 接入位置 |
|---|---|---|
| 前端 | 添加 PDF，展示导入状态及当前资料，支持更换或移除 | 扩展现有 Vue 页面 |
| 接口层 | 接收上传、列出知识库；研究请求增加可选 `knowledge_base_id` | 扩展 `main.py` |
| 知识库服务 | 解析、分块、向量入库；按查询返回相关片段和来源 | 新增服务，复用 HelloAgents RAG 管线 |
| 研究协调器 | 使用子任务查询词分别检索文档和网页，处理有效结果与错误 | 扩展 `agent.py` 的 `_execute_task()` |
| 证据整理 | 合并两类资料，保留出处、去重并限制上下文长度 | 扩展现有上下文整理逻辑 |
| 总结与报告 | 基于证据生成总结，沿用 NoteTool 保存笔记并汇总报告 | 扩展现有提示词和来源展示 |

首版支持 PDF，使用当前 HelloAgents 0.2.9 的文档处理、Embedding 与 Qdrant 检索能力。具体依赖与服务配置在实施前核对。

实现说明：复用 HelloAgents 的 PDF 解析分块与 Embedding；向量存储直接使用 Qdrant 客户端，以支持默认的本地持久化和明确的入库结果核对。每次导入一个 PDF，生成一个独立知识库；前端自动关联本次导入结果，暂不提供历史资料选择。未配置外部 Qdrant 时无需启动数据库服务。

## 3 四个接入重点

1. **导入与研究分开。** 解析、向量入库成功后才将知识库标记为可用，并自动关联当前研究。研究请求引用该知识库 ID；移除只解除关联，不删除已保存的资料。
2. **检索后交给原有总结 Agent。** 复用底层 RAG 管线获取片段和元数据，与网页内容一起构建上下文。知识库服务负责检索，答案由现有总结与报告流程生成。
3. **按两类资料判断是否继续。** 网页无结果或搜索失败时，只要文档检索有有效证据，任务仍可继续；反之亦然。两边都无有效证据时说明资料不足，并区分无结果与工具失败。
4. **来源与数据隔离。** 证据保留来源类型、文件名或网页 URL、章节及片段标识；页码仅在解析结果可靠提供时使用。知识库 ID 映射到明确的命名空间，入库和检索都显式指定；研究笔记也按研究范围隔离。

NoteTool 继续负责过程笔记，Qdrant 负责文档片段检索。首版复用现有 Vue 界面，不引入第八章的 Gradio 界面和整套 MemoryTool。

## 4 实施与验收

讨论确认后按以下顺序实施：

1. 文档导入、知识库管理及片段检索。
2. 接入子任务执行，合并文档与网页证据，调整无结果分支。
3. 前端 PDF 添加与移除入口、来源展示及 SSE 状态反馈。
4. 验证以下场景后，再更新项目说明和项目经验。

验收场景：

- 不添加资料：现有联网研究可正常执行。
- 仅文档有证据：网页无结果或失败时仍可生成有文档依据的总结。
- 文档与网页都有证据：报告分别列出可定位的引用来源。
- 两边均无证据：如实说明不足，不生成无依据的结论。
- 不同知识库：检索结果不混入其他知识库资料。

MQE、HyDE 等扩展策略在基础检索链路验证后，再按效果和耗时决定是否启用。

## 5 代码实现约定

- **后续验收由用户进行。** 按用户最新要求，后续修改完成后不主动运行自动化测试；说明改动与使用方式，由用户提供真实任务验收。下方已有测试记录属于此前完成的历史验证。
- **注释简单易懂。** 使用简短中文注释，解释关键步骤在做什么、为什么这样处理；重点说明文档入库、命名空间隔离、证据合并和异常分支。
- **流程直观。** 优先使用清晰的函数、变量名和直接的调用顺序，让代码能对应上面的流程图；函数过长时按明确职责拆分。
- **沿用现有结构。** 在现有接口、服务层、协调器和 Vue 页面中接入 RAG，复用 HelloAgents 已有能力，避免为首版引入多层封装或复杂调度机制。
- **关键判断写清楚。** 明确区分入库成功、检索无结果和工具失败，让读代码的人能看懂任务为什么继续、跳过或报错。
- **核心阶段记录日志。** 沿用 Python logging，在文档上传、解析分块、向量入库、研究规划、文档与网页检索、证据整理、任务总结、笔记保存和报告生成时记录开始、结果及耗时；异常记录原因与堆栈。使用研究 ID、任务 ID 和知识库 ID 关联日志，便于排查；日志不输出密钥或整份文档正文。

日志文件：`.runtime/logs/research.log`，按大小轮转。导入资料和向量数据保存在 `.runtime/knowledge_bases/`；研究笔记在各研究独立目录中保存。

引用展示：页面和报告统一使用 `[1]`、`[2]`，参考来源列出文件名或网页标题，并注明“文档”或“网页”。同一研究中的相同证据复用一个数字编号；内部继续保存任务证据编号，用于校验和排查。

DeepSeek 工具调用兼容：模型回复中的已知 DSML 工具标记先转换为 HelloAgents 0.2.9 的 `[TOOL_CALL:...]` 格式，再交给框架执行。无法识别的格式不会执行，会提示模型重新输出，最多尝试三次；仍失败则报错。日志只记录格式特征，不记录工具参数正文。为保证工具参数完整，按一轮模型回复归一后发送总结；任务和工具阶段仍通过 SSE 实时展示。

Embedding 排查与限流处理：DashScope SDK 模式记录状态码和错误代码，不记录密钥或请求正文；遇到 429 或服务端错误时最多尝试三次。2026 年 10 月 30 日的真实研究中，旧日志未记录具体错误状态；针对同一失败子任务方向的单独请求返回 400 / Arrearage（账户欠费）。原始查询词未留存，这一请求不是逐字重放。
